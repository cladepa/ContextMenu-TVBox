# HANDOFF — читай это первым делом в новом чате

Это проект Paolo: кастомное контекстное меню (замена ПКМ) для Android TV box без
физической правой кнопки на пульте-аэромыши, плюс кросс-девайсный буфер обмена
через Syncthing, индикатор мигания и история буфера. Разговор с историей всей
разработки был очень длинным (несколько дней), и песочница Claude сбрасывалась
дважды — предположительно из-за длины сессии. Поэтому: **если сборка/тесты снова
начнут спотыкаться на пустом месте — не пытайся тянуть один и тот же чат
бесконечно, предложи Paolo начать новый, отталкиваясь от этого файла.**

Стиль общения: по-русски, без нотаций про токены/безопасность — Paolo в курсе,
упоминай факт коротко один раз и двигайся дальше, не read moralей.

## Первые шаги в новой сессии

1. Клонировать репозиторий: `github.com/cladepa/ContextMenu-TVBox` (приватный).
   Нужен свежий fine-grained PAT от Paolo (Contents: Read and write, только этот
   репозиторий) — попроси, если его нет в контексте.
2. Поставить тулчейн (слетает вместе с песочницей каждый раз):
   ```
   apt-get update
   apt-get install -y aapt dalvik-exchange default-jdk-headless zipalign apksigner libandroid-23-java
   ```
   `android.jar` окажется в `/usr/lib/android-sdk/platforms/android-23/android.jar`.
3. Попросить Paolo прислать `debug.keystore` — он держит его локально именно на
   этот случай. **Не генерировать новый** — другая подпись = Android не даст
   поставить APK поверх уже установленного на боксе, придётся удалять текущую
   версию. Генерировать новый — только если он говорит, что файла нет.
4. Собрать по инструкции ниже, проверить что компилируется, и только потом
   продолжать фичи с того места, где остановились (см. ToDo).
5. После КАЖДОЙ рабочей сборки — сразу коммit + push в GitHub, не откладывая.
   `uploads.github.com` (для настоящих GitHub Releases) заблокирован сетевыми
   правилами песочницы (403 Host not in allowlist) — обходной путь: класть
   собранный APK прямо в `releases/` в самом репозитории (`.gitignore` уже не
   исключает `*.apk`) и коммитить туда же.

## Сборка (ручной пайплайн, без Android Studio/Gradle)

```
PROJ=~/contextmenu_roottest   # разложить файлы из репо сюда: src/, res/, AndroidManifest.xml
ANDROID_JAR=/usr/lib/android-sdk/platforms/android-23/android.jar
BUILD=~/contextmenu_roottest_build

aapt package -f -m -J $BUILD/gen -M $PROJ/AndroidManifest.xml -S $PROJ/res \
    -I $ANDROID_JAR -F $BUILD/apk/resources.ap_

javac -source 1.8 -target 1.8 -classpath $ANDROID_JAR -sourcepath $PROJ/src \
    -d $BUILD/obj $PROJ/src/com/cladepa/contextmenu/*.java

dalvik-exchange --dex --min-sdk-version=13 --output=$BUILD/dex/classes.dex $BUILD/obj

cp $BUILD/apk/resources.ap_ $BUILD/apk/unsigned.apk
cd $BUILD/dex && zip -u ../apk/unsigned.apk classes.dex && cd -
zipalign -f 4 $BUILD/apk/unsigned.apk $BUILD/apk/aligned.apk

apksigner sign --ks $BUILD/debug.keystore --ks-pass pass:android --key-pass pass:android \
    --ks-key-alias androiddebugkey --out $BUILD/apk/ContextMenu.apk $BUILD/apk/aligned.apk
```

**Железные ограничения этой платформы** (API 23 — единственный доступный jar):
- НИКАКИХ лямбд — `dalvik-exchange --min-sdk-version=13` роняет их в рантайме
  через `LambdaMetafactory`. Только анонимные классы.
- Никакого androidx.
- Всё, что появилось после API 23 (`TYPE_APPLICATION_OVERLAY`,
  `Settings.Global.DEVICE_NAME`-константа и т.п.) — доставать через сырые
  int/строковые литералы, не через SDK-символы (их просто нет в jar).
- UI полностью программный, ни одного XML layout (кроме самого манифеста).

**Про `HelperScripts.java`** — там зашиты `DISCOVER_MENU_SH` и `NOTIFY_TVBOX_SH`
как java-строки. НИКОГДА не редактировать эти строки руками (посчитать
экранирование backslash'ей в regex/awk — верный способ внести баг). Вместо
этого: написать/поправить настоящий `.sh`-файл, прогнать через маленький
python-скрипт, который генерирует java-строку и сразу же проверяет
побайтовое совпадение через обратное декодирование. Пример такого скрипта
есть в истории разговора, воспроизвести несложно (split by `\n`, экранировать
`\`/`"`, склеить через `" +\n"`).

## Архитектура (что где лежит)

- `MainActivity.java` — экран настроек: имя устройства (с каскадным
  переименованием файлов), путь буфера, путь `.stfolder`, избранные устройства
  (чек-лист с автосканом папки), устройства ввода мышь/клавиатура (чек-лист по
  возможностям, автосброс кнопкой), настройки мигания (угол/цвет/размер/
  количество/период + отдельно размер шрифта истории), кнопка установки
  скриптов на бокс, root-тест, справка по способам вызова.
- `OverlayManager.java` — само контекстное меню: попап у курсора, D-pad + мышь,
  вложенные пункты (`Item` с `children`). Пункты: Копировать/Вырезать/Вставить/
  Выделить всё/Поделиться/История/"Вставить из ›"/"Отправить в ›". Там же
  `flash()`/`flashWith()` — логика мигающего индикатора.
- `HistoryOverlay.java` — отдельное перетаскиваемое/растягиваемое окно истории
  (`clip_hist-<имя>.txt` этого устройства), обрезка записей до 3 строк, клик/
  D-pad = вставить. Положение/размер сохраняются в Prefs между запусками.
- `CommandReceiver.java` — точка входа по broadcast (`tv.contextmenu.SHOW` /
  `HIDE` / `FLASH`).
- `MenuTrigger.java` — общая логика "определить курсор+устройства через
  discover_menu.sh, потом показать меню" (используется и receiver'ом, и
  activity).
- `TriggerActivity.java` / `FlashTriggerActivity.java` — невидимые Activity-
  триггеры. **Activity надёжнее для МЕНЮ** (подтверждено через tvQuickActions),
  но **НЕ работает для мигания** даже под root (похоже на ограничение
  background activity launch) — для мигания использовать только broadcast.
- `UsbEventReceiver.java` — на ATTACHED/DETACHED донглов пересканирует и сам
  добавляет/убирает устройства из списков мыши/клавиатуры.
- `InputDeviceScanner.java` — поиск устройств по возможностям: мышь =
  `REL_X`+`REL_Y`+`BTN_MOUSE`, клавиатура = `KEY_A`+`KEY_LEFTCTRL` (парсинг
  `getevent -lp`).
- `Prefs.java` — все настройки (SharedPreferences).
- `Root.java` — общий helper `su 0 sh -c "cmd"` → строка вывода.

## Специфика этого конкретного бокса

- `su` экзотический: `/system/xbin/su`, синтаксис `su <uid> sh -c "команда"`
  или `su <uid> sh /путь/script.sh` — НЕ `su -c`.
- Донгл пульта-аэромыши = `HAOBO Technology USB Composite Device` (мышь) +
  `...Keyboard` (та же физическая железка, отдельный HID-интерфейс клавиатуры
  — подтверждено тестом с отключённой отдельной клавиатурой-тачпадом).
- Курсор: `dumpsys input`, брать запись с МИНИМАЛЬНЫМ `age=` (там несколько
  параллельных буферов на разные окна, наивный grep+tail берёт не ту).
  Обязательно "дёрнуть" мышь (`sendevent` REL_X +1/-1) прямо перед чтением —
  иначе позиция протухает после простоя курсора.
- Устройства ввода теперь ищутся ОДНИМ проходом по списку сохранённых имён
  (было — по проходу на каждое сохранённое имя, это давало заметные тормоза
  при нескольких включённых устройствах).
- Фоновое чтение/запись системного буфера обмена (в обход ограничения
  Android 10+ на фокус) — через `app_process`, самопонижение root до UID 2000
  ("com.android.shell"), `/data/local/tmp/clip.jar` (dex-байткод, источник —
  github.com/polygraphene/adb-clip):
  ```
  ANDROID_ROOT=/system ANDROID_DATA=/data CLASSPATH=/data/local/tmp/clip.jar \
      app_process /system/bin Clip ["текст, если запись"]
  ```
- `am broadcast` **обязательно с `--user 0`**, иначе непривилегированные
  вызывающие (например Syncthing-Fork, у него свой обычный UID приложения)
  получат `SecurityException` — broadcast без этого флага по умолчанию метит
  во всех пользователей системы, это требует спецправа, которого у обычных
  приложений нет. root/shell это право имеют неявно, поэтому у Paolo при
  ручных тестах всё работало, а у Syncthing-Fork — нет, пока не нашли этот
  флаг.
- Syncthing-Fork (v2.0.10) реально умеет запускать скрипт после синхронизации
  папки: кладётся в `.stfolder/<имя>.sh` (служебная папка, которую сам
  Syncthing создаёт в корне синкаемого правила), плюс тумблер "Запустить
  скрипт" включить в настройках именно этой папки. Вызывает как
  `sh script.sh sync_complete`. Root он не использует (сам разработчик выпилил
  поддержку root из соображений безопасности) — работает от своего обычного
  UID приложения (был `u0a131` на момент теста, может отличаться при
  переустановке).

## Конвенция имён файлов буфера

Папка настраивается (`Prefs.bufferDir`, дефолт
`/storage/emulated/0/Zametki_ALL/claude_bufer`), внутри:
- `<имя_устройства>.txt` — исходящий (чем устройство делится), обновляется
  автоматически при локальном Копировать/Вырезать.
- `to_<имя_устройства>.txt` — входящий, адресованный этому устройству.
- `to_all.txt` — общий входящий, всегда в меню как "Всем" безусловно.
- `clip_hist-<имя_устройства>.txt` — растущая история этого устройства
  (только этот девайс туда пишет — конфликтов Syncthing быть не может).
  Формат записи: `===ENTRY 2026-08-19T04:07:33===\n<текст>\n`.

Имя устройства — настраивается в MainActivity (дефолт из
`Settings.Global` device_name через сырой строковый ключ, т.к. константы нет
в API 23). При переименовании — все три типа файлов переезжают через `mv`,
не дублируются.

## Пофикшенные баги (не наступать заново)

- **НИКОГДА** не делать `input tap X Y` перед вставкой ради "рефокуса" —
  позиция курсора мыши и текстовая каретка это разные вещи, тап ломает
  позицию вставки. Просто `input keyevent 279` напрямую.
- **НИКОГДА** не вставлять произвольный текст (буфер/история) прямо в
  shell-строку с наивным экранированием кавычек — это инъекция. Всегда
  base64 в Java → декод на устройстве (см. `HistoryOverlay.selectEntry()`).
- `--user 0` нужен на ВСЕХ `am broadcast`, которые должны работать не только
  из-под root.
- Каждую su-команду начинать со свежего `su 0 sh -c "..."`, а не полагаться
  на уже открытую интерактивную сессию — та может тащить свой
  `LD_LIBRARY_PATH` и ломать линковку (`app_process` падал именно из-за
  этого один раз).

## Общая методология (как мы тут работаем)

- Тестировать шаг или небольшую группу шагов, потом двигаться дальше — не
  наваливать много непроверенных фич разом.
- При любом сомнении — просить у Paolo диагностику (лог, `dumpsys`, тайминг
  через `time`), не гадать. Почти каждый серьёзный баг в этом проекте ловился
  именно так, а не с первой попытки угадывания причины.
- Paolo — опытный технарь (Android-разработчик, любит разбираться в
  механизме, а не просто получать рабочий результат), объяснять "почему", а
  не только "что делать".
